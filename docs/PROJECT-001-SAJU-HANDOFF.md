## 2. 현재 설계 원칙

향후 기능은 아래 원칙을 깨지 않는 범위에서 추가한다.

### 2.1 출생정보 모델 단일화

사주와 궁합은 동일한 출생정보 구조를 사용한다.

```ts
type BirthProfile = {
  name?: string;
  gender: 'male' | 'female';
  calendarType: 'solar' | 'lunar';
  birthDate: string;
  birthTime: string;
  timeKnown: boolean;
  leapMonth: boolean;
};
```

새 기능에서 생년월일 입력 폼을 별도로 다시 만들지 말고 이 모델을 재사용한다.

### 2.2 계산과 UI 분리

핵심 계산은 UI 이벤트 안에 직접 작성하지 않는다.

권장 구조:

```text
BirthProfile
   ↓
validateBirthProfile()
   ↓
calculateSaju()
   ↓
SajuChart
   ├─ individual reading
   ├─ compatibility
   ├─ annual fortune
   ├─ daewoon
   └─ AI interpretation
```

### 2.3 성별 처리

성별은 프로필, 궁합 표시, 향후 대운 계산에 필요한 값이다.

현재 기본 원국을 임의로 성별에 따라 변경하지 않는다. 앞으로 대운 등 성별 규칙이 실제로 필요한 계산에만 반영한다.

### 2.4 출생시간 미상

시간 미상일 때 시주를 임의의 정오 시주로 사용자에게 보여주지 않는다.

계산 라이브러리 내부 처리를 위해 임시 시간을 사용할 수는 있으나 결과에서는 시주를 제외하고 `6글자 기준`임을 표시한다.

### 2.5 궁합 점수 정책

궁합 점수는 미래 관계 성공 여부를 예측하는 값으로 표현하지 않는다.

현재 4개 축:

1. 오행 조화
2. 상호 보완
3. 일간 관계
4. 음양 리듬

최종 점수는 관계 유형에 따른 가중 평균이다.

향후 점수를 고도화할 때는 반드시:

- 산출 근거를 사용자에게 노출
- 특정 성별 조합 자체에 임의 가산점/감점 금지
- 한 개 총점보다 세부 축을 우선
- 점수와 해석 문장을 같은 계산 결과에서 생성

## 3. 다음 고도화 우선순위

### Phase A — 계산 신뢰성 강화

가장 먼저 할 작업이다.

- 절입 시점 기준 월주 검증
- 한국 표준시 처리 정책 명시
- 해외 출생 지역 / 시차 지원 여부 결정
- 자시(23시) 일주 변경 정책 검증
- 음력 윤달 테스트 케이스 확대
- 1900년 이전 / 미래 날짜 지원 범위 정의
- 동일 입력에 대한 회귀 테스트 작성
- 유명 만세력 결과와 샘플 비교

완료 기준:

- 고정 샘플 20~50건 테스트 데이터 보유
- 라이브러리 버전 변경 시 결과 차이를 자동 탐지

### Phase B — 사주 결과 고도화

추천 순서:

1. 십성
2. 지장간
3. 천간 합·충
4. 지지 합·충·형·파·해
5. 계절 / 월령 기반 강약 참고값
6. 신강·신약 참고 지표
7. 용신 관련 기능은 충분한 검증 후 별도 단계에서 도입

주의:

`오행이 가장 적다 = 용신`으로 처리하면 안 된다.

현재의 `보완 오행`은 간단한 UX 지표이므로 정밀 명리 판정과 명확히 분리한다.

### Phase C — 운세 기능

추가 후보:

- 올해운
- 월별 흐름
- 재물운
- 직업/이직운
- 연애운
- 건강 관련 생활 리듬 안내
- 대운
- 세운

구조 권장:

```text
SajuChart + targetDate
        ↓
FortuneEngine
        ↓
AnnualFortune / MonthlyFortune
```

현재 날짜를 프론트에서 임의로 섞지 말고 계산 함수의 입력값으로 명확하게 전달한다.

### Phase D — 궁합 고도화

현재 4축을 기반으로 다음 결과를 분리한다.

#### 연애궁합

- 감정 표현 방식
- 연락 / 거리감
- 애정 확인 방식
- 갈등 회복 방식

#### 결혼궁합

- 생활 리듬
- 돈 관리
- 역할 분담
- 장기 의사결정
- 갈등 누적 가능 영역

#### 친구궁합

- 활동 스타일
- 대화 방식
- 독립성
- 친밀도 유지 방식

#### 직장·동료궁합

- 업무 속도
- 의사결정
- 리더십 / 팔로워십
- 피드백 방식
- 역할 보완

향후에는 단순 문구 추가가 아니라 `CompatibilityResult`에 도메인별 세부 결과를 구조화한다.

예:

```ts
type CompatibilityDetail = {
  communication: number;
  emotionalRhythm: number;
  lifestyle: number;
  moneyStyle?: number;
  conflictStyle: number;
};
```

## 4. AI 해석 고도화

AI는 계산을 대신하면 안 된다.

정확한 흐름:

```text
사용자 입력
→ 결정적 계산 엔진
→ 구조화된 JSON 결과
→ AI가 자연어 해석
```

AI 프롬프트에 원본 생년월일만 넘기고 모델이 직접 사주를 계산하게 하지 않는다.

추천 AI 결과 구조:

```json
{
  "summary": "",
  "personality": "",
  "career": "",
  "money": "",
  "relationship": "",
  "balance_actions": [],
  "cautions": []
}
```

궁합도 동일하게 구조화된 계산값을 전달한다.

## 6. 개인정보 원칙

생년월일과 출생시간은 민감하게 느껴질 수 있는 개인 데이터이므로 최소 수집한다.

원칙:

- URL query string에 생년월일/출생시간 포함 금지
- 공유 URL에 개인 입력값 포함 금지
- 서버 저장은 기능상 필요한 경우에만 도입
- 저장 기능 도입 시 삭제 기능 제공
- AI 호출 시 필요한 최소 데이터만 전송
- 분석/로그에 원본 생년월일을 그대로 저장하지 않는 방안 검토
